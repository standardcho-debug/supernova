# supernova — 고객사 SNS 콘텐츠 생성 파이프라인 (프로토타입)

코파운더 고객사의 히스토리(사업계획·요구사항·불만사항·매출현황)를 근거로 네이버 블로그·인스타그램·유튜브
콘텐츠를 텍스트+이미지까지 완성도 있게 만드는 파이프라인의 프로토타입입니다.

## 지금 실사용 대상: PRD v1.0 마케팅 에이전트 (`web/marketing_app.py`)

아래 섹션들은 이 저장소의 **첫 번째 프로토타입**(가상 픽스처 고객사 `demo-bakery` 기반)을 설명합니다.
현재 STan이 직접 쓰는 것은 PRD v1.0("코파운더 마케팅 에이전트")으로, 실제 co-mcp 데이터(현재는
`supernova-platform` 실측 녹화 픽스처)를 근거로 인스타그램 콘텐츠를 만드는 별도 트랙입니다 —
데이터 모델·화면이 전혀 다릅니다. 실행:

```bash
pip install -r requirements.txt
uvicorn web.marketing_app:app --reload --port 8001
# http://127.0.0.1:8001 → 맥락(F1) → 전략 확인(F2) → 브리프·크리에이티브 생성(F3/F4) → 승인(F5)
# 한 화면(Split-View)에서 순서대로 진행. 발행 버튼은 없음 — 승인까지가 이 화면의 경계.
```

- `ANTHROPIC_API_KEY`를 설정하면 실제 Claude로 전략/브리프/카피/루브릭을 생성하고, 없으면
  `TemplateLLMClientV1`(오프라인 고정 출력)로 흐름만 데모합니다.
- `PLAYWRIGHT_CHROMIUM_PATH`를 설정하면 캐러셀 슬라이드를 실제 PNG로 렌더링합니다(없으면 텍스트만).
- co-mcp 실 네트워크 인증(`COFOUNDER_MCP_TOKEN`)은 아직 확정되지 않았습니다(PRD §9 Q1) — 기본은
  `sns_marketing_agent/fixtures/cofounder_recorded/supernova-platform/`에 저장된 실제 녹화
  데이터로 동작합니다.
- 절대 제약(C1-C6: 시스템맵 읽기전용, 원가/수익식 미입력, co-mcp 쓰기 없음, 타 고객사명·금액 마스킹,
  `open_to_client:false` 규칙 비노출, 발행/광고 집행 없음)은 `sns_marketing_agent/cofounder_client.py`,
  `masking_filter.py`, `review_queue.py`에 코드로 강제돼 있고 각 모듈 테스트로 검증됩니다.
- 상태는 `web/data/reviews_v1.db`(승인/반려 결정)에는 영속되지만, 생성된 브리프·카피 본문 자체는
  현재 프로세스 메모리에만 있습니다(재시작하면 사라짐) — 로컬 파일럿 단계의 알려진 한계입니다.

## 이 저장소가 전체 로드맵에서 차지하는 위치

목표는 SNS 운영 자체가 아니라 그 다음 단계인 **채널 연결·업로드 자동화 → 광고 퍼포먼스 마케팅 자동화**
입니다. 다만 광고가 먹히려면 그 전에 SNS 채널 자체가 신뢰도 있게 운영되고 있어야 하고, 그러려면 콘텐츠가
"초안"이 아니라 "그대로 써도 되는 완성본" 수준이어야 합니다. 이 저장소는 그 완성본을 만드는 부분만
다룹니다.

| 단계 | 내용 | 이 저장소에 포함? |
|---|---|---|
| 1. 히스토리 수집 | 고객사 문서를 `ClientProfile`로 정규화 | O |
| 2. 브리프 생성 | 히스토리 근거를 인용한 채널별 소재 제안 | O |
| 3a. 텍스트 초안 | 채널별 카피/스크립트 생성 | O |
| 3b. 이미지 생성 | 카드뉴스·캐러셀·썸네일 PNG 렌더링 | O |
| 3c. 영상 | 유튜브 숏폼 스토리보드(장면·내레이션·길이) | O (스크립트까지만) |
| 3c. 영상, 실제 파일 | 실제 촬영/편집된 영상 파일 | **제외** |
| 4. 승인 게이트 | 대표 승인/반려 상태 관리 | O |
| 4-UI. 승인 화면 | 고객사 대표가 직접 보고 승인/반려하는 웹페이지 | O (`web/`, 프로토타입) |
| 5. 채널 연결·업로드 자동화 | 네이버 블로그/인스타/유튜브 실제 게시 | **제외** |
| 6. 퍼포먼스 마케팅 자동화 | 광고 집행·최적화 | **제외** |

**영상을 스크립트까지만 다루는 이유**: 이 세션/저장소의 도구셋에 실제 영상을 생성·편집하는 기능이 없습니다.
"완성도 높은 영상"을 약속해놓고 스토리보드만 내놓으면 팀이 못 지키는 설계가 되므로, 지금 실제로 만들 수
있는 산출물(장면별 온스크린 텍스트 + 내레이션 + 길이)까지만 자동화 대상으로 명시했습니다. 실제 영상
렌더링은 별도 R&D(외부 영상생성 API 조사 등)로 다뤄야 합니다.

**5·6단계를 제외한 이유**: 각 채널의 공식 게시 API 연동, 계정 권한, 게시 정책은 별도 검토가 필요한
영역이고, 현재 팀에 매체 계정을 직접 운영해본 경험이 없다는 점(사업계획서에 명시된 공백)과도 맞물립니다.
`ApprovalGate`에 `publish()`가 없는 것은 실수가 아니라 의도입니다.

## 설계 원칙

- **근거 없는 소재 금지**: `ContentBrief.source_evidence`는 고객사 히스토리에서 실제로 나온 문구를
  인용해야 합니다. 근거 없이 일반적인 마케팅 문구를 만들면 대행사와 다를 게 없다는 것이 사업계획서의
  핵심 차별점이라, 이 필드를 필수로 뒀습니다.
- **대표 승인은 축소가 아니라 유지**: 자동화가 없애는 것은 브리핑·왕복이지, 대외 콘텐츠 최종 확인이
  아닙니다. `ApprovalGate`는 이 경계를 코드로 강제합니다.
- **정보성 이미지는 생성이 아니라 렌더링**: `image_generator.py`는 프롬프트로 그림을 그리게 하지
  않고, 정해진 텍스트를 HTML로 배치해 스크린샷 찍는 방식(Cofounder의 instagram-cards/blog-card
  스킬이 이미 검증한 접근)을 씁니다. 자유생성 이미지 모델은 숫자·문구를 왜곡할 수 있어 정보 전달용
  카드에는 부적합합니다.
- **LLM/데이터소스/이미지렌더러는 인터페이스로 분리**: `HistorySource`, `LLMClient`,
  `ImageAssetGenerator`는 프로토콜(protocol)입니다. 실제 Cofounder 연동·실제 모델 호출·실제
  브라우저 렌더링은 이 인터페이스 뒤에서 나중에 갈아끼울 수 있고, 지금은 `StaticHistorySource`
  (JSON 픽스처)·`TemplateLLMClient`(고정 출력)·`NullImageGenerator`(렌더링 없이 계획만)로
  네트워크·API 키·브라우저 설치 없이 전체 흐름을 실행·테스트할 수 있습니다.

## 고객사 화면 (`web/`)

FastAPI로 만든 승인함 페이지입니다. 고객사 대표가 보는 화면은 stage 1~3(자동화)이 아니라 이 화면
하나뿐입니다 — 준비된 콘텐츠를 이미지까지 보고, 승인하거나 반려 사유를 남깁니다.

```bash
pip install -r requirements.txt
uvicorn web.app:app --reload
# http://127.0.0.1:8000 → /admin (Stan용: 고객사별 링크 목록)
# 링크를 클릭하면 /clients/demo-bakery?token=... 로 이동 — 고객사가 보는 화면
```

상태는 `web/data/`(git에는 안 올라감)에 sqlite로 저장돼서 **서버를 껐다 켜도 승인/반려 이력이
남습니다** — 직접 승인 눌러보고 서버 재시작한 뒤 다시 들어가서 확인해보시면 됩니다. 리셋하고
싶으면 `web/data/` 폴더를 지우면 됩니다.

각 고객사에는 랜덤 토큰이 발급되고(`web/access.py`), 그 토큰이 없으면 `/clients/<client_id>`가
403을 돌려줍니다 — `demo-bakery`인 걸 안다고 남의 승인함을 볼 수는 없다는 뜻입니다. 토큰은
`/admin`에서 확인합니다.

**알려진 한계 (프로토타입 단계, "진짜 인증"은 아직 아님)**:
- 로그인 없이 토큰(긴 랜덤 문자열)을 URL에 붙이는 방식입니다. 계약서 서명 링크와 비슷한 수준의
  보안이지, 비밀번호 로그인 수준은 아닙니다. 링크가 유출되면 그 고객사 승인함은 노출됩니다.
- 토큰 만료·재발급·고객사가 직접 링크를 무효화하는 기능이 없습니다.
- `/admin`에 접근 제한이 없습니다 — 이 서버에 접근할 수 있는 사람은 모든 고객사 링크를 볼 수
  있습니다. Stan이 로컬에서 혼자 돌리는 지금 단계에서만 괜찮습니다.
- 지금은 픽스처 고객사(`demo-bakery`) 하나만 시작 시 자동으로 채워집니다. 여러 실제 고객사를
  붙이려면 `CofounderHistorySource` 연동(아래 "아직 안 되어 있는 것" 참고)이 먼저 되어야 합니다.

## 아직 안 되어 있는 것 (다음 단계로 넘길 것)

- `CofounderHistorySource`는 `DocumentsFetcher` 인터페이스만 정의했고, 실제 Cofounder MCP
  문서 조회(`search_documents`/`list_documents`)와 연결하는 구현체는 없습니다.
- `AnthropicLLMClient`는 실제 SDK 호출 골격만 있고, 브리프/초안 생성 프롬프트가 실제로 안정적인
  JSON을 반환하는지는 검증되지 않았습니다(현재는 JSON 파싱 실패 시 그대로 에러를 던집니다 — 재시도나
  포맷 교정 로직 없음).
- 채널별 "불만사항→소재" 분류(`CofounderHistorySource`의 `bug` 키워드 매칭)는 임시 규칙이며,
  실제 Cofounder 문서 스키마에 맞는 태깅 체계로 교체가 필요합니다.
- 이미지는 텍스트 카드 수준입니다. 배경 사진·일러스트·브랜드 로고 합성 같은 실제 "비주얼 완성도"는
  다루지 않습니다 — 필요해지면 별도 자산(로고, 상품 사진) 입력을 받는 확장이 먼저 필요합니다.
- 영상은 스토리보드까지만 — 위 표 설명대로 실제 영상 파일 생성은 범위 밖입니다.
- 실제 고객사 데이터는 이 저장소에 넣지 않았습니다(`sns_marketing_agent/fixtures/`는 가상 예시).
  실제 연동 테스트는 Cofounder 접근 권한이 있는 별도 환경에서 진행해야 합니다.

## 실행

```bash
pip install -r requirements.txt
python -m sns_marketing_agent.pipeline --client-id demo-bakery --channels naver_blog instagram youtube
pytest
```

이미지 실제 렌더링까지 보려면 Playwright가 필요합니다:

```bash
pip install playwright && playwright install chromium
python -m sns_marketing_agent.pipeline --render-images ./out_images
```
