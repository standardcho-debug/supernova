# 세팅 가이드 — 새 PM 의 작업 환경 구성

> 이 문서는 **PM 본인의 클로드가 읽고 그대로 실행**하도록 쓰였다. 사람이 읽어도 된다.
> 막히면 임의로 우회하지 말고 **운영자에게 물어라** — 이 함대는 우회가 사고를 만든다.

## 0. 이게 무엇인가

`supernova-core` — SI 함대의 **중립 코어**다. 운영 규칙(CLAUDE.md)·에이전트·슬래시
커맨드·훅·보일러플레이트·플레이북·결정 기록이 들어 있다.

**여기 없는 것과 그 이유:**

| 없는 것 | 왜 |
|---|---|
| 클라이언트 제품 코드 | 각 클라 repo 에 있다. 담당 repo 에 GitHub collaborator 로 초대받아야 받는다 |
| 클라이언트 인프라(OpenTofu) | 그 클라 repo 의 `infra/` 에 있다 |
| 인프라 좌표(인스턴스 id·RDS 주소) | **플랫폼이 런타임에 준다.** repo 에 두면 담당 아닌 클라 것까지 모두에게 보인다 |
| AWS 자격 | 담당 클라 것만 운영자에게 따로 받는다 |

## 1. 필요한 것

| 도구 | 용도 | 확인 |
|---|---|---|
| git | 버전 관리 | `git --version` |
| Python 3.11+ | 게이팅 스크립트 | `python3 --version` |
| Node 20+ / npx | Playwright MCP(브라우저 검증) | `node --version` |
| jq | 안전 훅 일부가 사용 | `jq --version` |
| AWS CLI v2 | 담당 클라 접속(자격을 받은 뒤) | `aws --version` |

없어도 대부분의 문서 작업은 된다. **먼저 2~4단계를 끝내고, 막히는 도구만 그때 설치한다.**

## 2. 배치

압축을 풀고 작업 폴더로 옮긴다. 경로는 자유지만 **한글·공백 없는 경로**를 권한다.

```bash
mv supernova-core ~/projects/supernova-core
cd ~/projects/supernova-core
```

## 3. 플랫폼 토큰 (가장 중요)

운영자에게 **개인 토큰(PAT)** 을 따로 받는다. 이 압축 파일에는 들어 있지 않다 —
토큰은 곧 신원이라 파일로 돌리지 않는다.

받은 토큰을 셸 환경변수 `SPNV_PLATFORM_TOKEN` 으로 넣는다. 예(zsh):

```bash
echo 'export SPNV_PLATFORM_TOKEN="spnv_여기에_받은_토큰"' >> ~/.zshrc
source ~/.zshrc
```

⚠️ **이 값을 repo 안의 파일에 적지 마라.** `.mcp.json` 은 `${SPNV_PLATFORM_TOKEN}` 으로
환경변수를 참조하도록 이미 돼 있다.

확인:

```bash
curl -sS -H "Authorization: Bearer $SPNV_PLATFORM_TOKEN" \
  "https://cofounder-api.jengablock.com/api/authz/deploy-check/?client=<담당-클라-slug>"
```

`<담당-클라-slug>` 은 운영자가 알려준 담당 클라이언트 중 하나로 바꾼다.
`{"can_deploy":...,"role":"pm",...}` 가 나오면 성공이다. 비어 있거나 오류면 토큰을
다시 확인한다.

## 4. 클로드 실행 + MCP 연결 확인

이 폴더에서 클로드를 띄우면 `.mcp.json` 의 MCP 서버가 자동으로 붙는다.
`CLAUDE.md` 도 자동으로 읽힌다 — **그 파일이 이 함대의 운영 규칙 정본이다.**

첫 확인 (클로드에게):

> `mcp__spnv-platform__list_clients` 를 호출해서 내가 담당하는 클라이언트를 보여줘.

담당으로 배정된 클라이언트만 나온다. 배정 안 된 곳은 조회해도 **빈 결과**가 나오며,
그게 정상이다(오류가 아니다).

## 5. 안전 훅 확인 (건너뛰지 마라)

이 저장소에는 사고를 물리적으로 막는 훅이 들어 있다 — 배포 정문 우회 차단, 클라
repo 오염 차단, worktree 규약 강제 등. 클로드를 처음 띄우면 **프로젝트 훅을 승인할지
묻는다. 승인해라.** 거절하면 안전장치 없이 일하게 된다.

훅이 실제로 동작하는지 확인:

```bash
python3 scripts/gating/test_block_raw_deploy.py
```

`Ran 21 tests ... OK` 가 나와야 한다. 실패하면 운영자에게 알린다 — 이 상태로
배포·클라 작업을 진행하지 마라.


## 6. 내가 할 수 있는 것과 없는 것

플랫폼이 서버에서 강제하므로, 규칙을 외울 필요 없이 **막히면 막힌 것**이다.

**할 수 있는 것**
- 담당 클라의 문서·로드맵·견적·지갑 조회, 요청/변경기록 작성
- 함대 공용 지식(`_system`·`_shared`) **읽기** — runbook 규약·크레딧 정책·개념 문서
- 담당 클라의 DB 터널 파라미터 조회(실제 접속엔 그 클라 AWS 자격이 따로 필요)

**할 수 없는 것 (설계상)**
- 담당 아닌 클라의 무엇이든 — 조회는 빈 결과, 쓰기는 거부
- 함대 공용 지식 **수정** — 규범 변경은 내부 결정 사항이다
- 배포 — 별도로 배포 권한을 받아야 한다(`can_deploy`)
- 비-additive 마이그레이션 승인 — 이건 항상 운영자만 한다

## 7. 작업 시작 전에 반드시 읽을 것 (사고 방지)

클로드에게:

> `mcp__spnv-platform__read_document` 로 `runbook/_system/local-environment-hazards.md`
> 를 읽고 요약해줘.

**로컬처럼 보이는 주소가 프로덕션 DB 인 경우**가 있다. 이 문서를 읽기 전에는
어떤 마이그레이션·시드 명령도 실행하지 마라.

## 8. 인바운드 처리 규칙 (핵심 한 가지)

클라이언트 요청이 들어오면 **바로 코드로 가지 않는다.** `CLAUDE.md` 의
"클라이언트 인바운드 routing" 절 순서를 따른다 — 특히 **step 0: 그 클라·그 요청
유형의 정본 절차(runbook)가 이미 있는지 먼저 조회**한다. 매번 절차를 새로 지어내는
것이 이 함대에서 가장 반복된 실수다.

## 9. 담당 클라 코드·자격 (운영자에게 요청)

- **GitHub**: 담당 클라 제품 repo 의 collaborator 초대. 플랫폼 권한과 **별개 축**이라
  자동으로 열리지 않는다.
- **AWS**: 담당 클라의 `[client-<slug>]` 프로파일. 클라이언트가 발급한 키이며
  담당 외 클라 것은 받지 않는다.

## 10. 업데이트

지금은 **압축 파일로 전달**된다. 새 압축을 받으면 기존 폴더를 통째로 교체하되,
본인이 만든 파일이 있으면 먼저 백업한다. GitHub 접근을 받으면 `git pull` 로 바뀐다.

버전은 `VERSION` 파일에 적혀 있다 — 운영자에게 문의할 때 그 값을 함께 알려라.

## 11. 막혔을 때

- **권한 오류**: 정상 동작일 가능성이 높다. 담당 배정이 필요한 것인지 운영자에게 확인.
- **MCP 가 안 붙는다**: 3단계의 토큰 확인 명령을 먼저 돌려본다.
- **절차를 모르겠다**: 지어내지 말고 `list_documents(kind="runbook")` 으로 찾는다.
  없으면 운영자에게 묻고, 알게 된 절차는 runbook 으로 남긴다(다음 사람의 자산).

# supernova — SI 클라이언트 포트폴리오 운영 베이스

여러 SI 클라이언트 프로젝트를 **한 명이 100개까지 운영 가능한 구조**로 끌고 가기 위한 함대 자산. 각 클라이언트는 자체 AWS 계정·본인 결제 카드를 보유 (AWS 비용 격리 원칙).

## 이 저장소가 들고 있는 것

| 디렉터리 / 파일 | 내용 |
|---|---|
| `CLAUDE.md` | 새 Claude Code 세션 진입점 (자동 로드되는 프로젝트 메모리) |
| `.claude/agents/` | Claude Code 함대 에이전트 정의 (`frontend-dev`, `backend-dev`, `infra`) |
| `.claude/commands/` | 슬래시 커맨드 (`/build-project` — PRD → 배포 오케스트레이션) |
| `docs/decisions/` | 큰 디자인 결정의 brainstorming 결과·이유 (날짜순) |
| `docs/prd/` | 클라이언트 PRD 보관 위치 |
| 플랫폼 `Client` 행 | 클라이언트별 상태·인프라 메타데이터 (`list_clients`). 좌표는 배포 정문의 `deploy-check` 로만 나간다 |

각 클라이언트 프로젝트 코드 자체 (`clients/banchan/`, `clients/dodam/` 등) 는 별도 관리되며 `.gitignore` 로 제외.

## 사용 방법

1. Claude Code 에서 이 디렉터리 (`si/`) 를 열면 `CLAUDE.md` 가 자동 로드됨.
2. 사용 가능한 함대·슬래시 커맨드를 즉시 인지.
3. 신규 프로젝트 의뢰가 들어오면:
   ```
   /build-project <client> docs/prd/prd-<client>.md
   ```
   → 6 Phase 워크플로우 진행 (3 사람 게이트 포함).

## 핵심 원칙

- **에이전트 간 직접 통신 없음** — 메인 컨텍스트가 오케스트레이터.
- **모든 핸드오프는 파일** — `outputs.json`, `schema.yml`, `registry.yaml`.
- **게이트 분기** — init·생성은 자율 (`tofu apply`, `git push` 자동), 모든 변경·삭제는 사람 게이트.
- **재현 가능 우선** — AWS 콘솔 직접 변경 금지.

자세한 룰·진화 패턴은 `CLAUDE.md` 와 `docs/decisions/` 참조.

## 진화 메모

- 디자인 결정의 *why* 는 `docs/decisions/` 에 누적.
- 함대 분화는 폴더가 아니라 **평면적 다중 `.md`** — 같은 위치에 자매 에이전트로 추가.
- 새 에이전트·커맨드 추가 후 첫 실전 호출 전 **텍스트 dry-run 필수** (회고: `docs/decisions/2026-05-28-build-project-dryrun.md`).
